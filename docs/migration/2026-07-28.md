## Summary of Breaking Changes

The 2026-07-28 RC is the most invasive revision since the protocol's first
release. Key changes:

1. **Stateless core**. The `initialize` / `notifications/initialized` handshake
   and the `Mcp-Session-Id` header are removed. Every request carries
   `io.modelcontextprotocol/protocolVersion` and
   `io.modelcontextprotocol/clientCapabilities` in `_meta` (plus `clientInfo`,
   SHOULD). Any request can land on any server instance. Servers needing
   cross-call state use explicit server-minted handles passed as ordinary tool
   arguments (SEP-2567) — not sessions.
2. **`server/discover`** is a **mandatory** RPC advertising supported versions,
   capabilities and identity.
3. **Multi Round-Trip Requests** (SEP-2322) replace server-initiated requests
   entirely. A server answers a `tools/call` / `resources/read` / `prompts/get`
   with an `InputRequiredResult` (`resultType: "input_required"`) carrying an
   `inputRequests` map and an opaque `requestState`; the client retries the
   original request — **with a new JSON-RPC id** — attaching `inputResponses`.
4. **`resultType` is required on every result**: `"complete"` normally,
   `"input_required"` for MRTR interim results.
5. **`subscriptions/listen`** replaces both the HTTP GET stream and
   `resources/subscribe` / `resources/unsubscribe`. One long-lived POST-response
   stream, opt-in per notification type.
6. **Required routing headers**: `Mcp-Method` on every POST, and `Mcp-Name` on
   the three methods that define it (`tools/call`, `prompts/get`,
   `resources/read`) — **not** on every POST. Plus `Mcp-Param-{Name}` mirrored
   from `x-mcp-header`-annotated tool parameters. Servers **MUST** validate
   headers against the body (`-32020`).
7. **Cache fields**: `ttlMs` and `cacheScope` (`"public"` | `"private"`) are
   **required** on `tools/list`, `prompts/list`, `resources/list`,
   `resources/read`, `resources/templates/list` via `CacheableResult`.
8. **Removed** (not deprecated): `ping`, `logging/setLevel`,
   `notifications/roots/list_changed`, SSE resumability (`Last-Event-ID`),
   `notifications/elicitation/complete` + `elicitationId`. Log level moves to a
   per-request `io.modelcontextprotocol/logLevel` in `_meta`.
9. **W3C Trace Context** formally documented (`traceparent`, `tracestate`,
   `baggage` in `_meta`).
10. **Extensions framework**: `extensions` field on `ClientCapabilities` and
    `ServerCapabilities`, reverse-DNS identifiers. Official extensions:
    - **MCP Apps** — server-rendered HTML UIs in sandboxed iframes.
    - **Tasks** (`io.modelcontextprotocol/tasks`) — poll-based `tasks/get`, new
      `tasks/update`, no `tasks/list`, unsolicited task handles allowed.
11. **Authorization hardening**: `iss` validation per RFC 9207 (**client-side
    MUST**), `application_type` at DCR, refresh-token handling, and credentials
    keyed by issuer (SEP-2352 — MUST re-register when the AS changes).
12. **Error codes**: missing-resource `-32002` → `-32602`, plus a formal
    allocation policy — `-32000`..`-32019` implementation-defined
    (grandfathered), `-32020`..`-32099` reserved for the spec.
13. **Deprecations** (12-month window): **Roots**, **Sampling**, **Logging**,
    the 2024-11-05 HTTP+SSE transport, `includeContext: "thisServer"` /
    `"allServers"`, and **DCR** (RFC 7591) in favour of CIMD.

## Review findings worth remembering

Two adversarial review rounds (Codex) caught things a careful reading of the
changelog alone did not. Recorded because each is a trap the next track can fall
into:

1. **The changelog is a summary, not the spec.** Its cache-fields entry lists
   five list/read methods; the caching page also requires them on
   `server/discover`. Read the feature page, not the changelog line.
2. **`-32002` is forbidden, not grandfathered.** The allocation policy reads
   like `-32000`..`-32019` is a safe legacy sandbox. It is not: new
   implementations **SHOULD NOT** use that sub-range at all, and **MUST NOT**
   emit `-32002` specifically, because 2025-11-25 used it for
   resource-not-found. Our 401/403/ session codes now live outside the reserved
   range entirely (`-31401`, `-31403`, `-31404`).
3. **`clientCapabilities` is required, `clientInfo` is not.** Easy to conflate —
   the `_meta` table marks one Yes and the other No.
4. **Gating on the transport is not gating on the version.** The stateless
   transport accepts `2025-06-18` and `2025-11-25` too, so every 2026-only
   behaviour must key off the negotiated version.
5. **`MCP-Protocol-Version` predates 2026.** It exists since `2025-06-18`; the
   omit-it grace applies only to clients older than that. Exempting "legacy"
   peers from it was wrong.
6. **A validator wired to one registration path is a bypass.** Annotations were
   collected in `registerTools` but not `registerTool`/`registerToolLive`.
7. **Tests can codify non-conformance.** Two of ours positively asserted the
   wrong behaviour (a headerless peer accepted, forbidden annotation placements
   ignored). A green suite proved nothing until they were inverted.

## Recommended Order

Derived from the dependency graph, not from effort. **H first**: it is the
cheapest track per site and every other track emits results, so landing the
envelope late means rewriting whatever B, C and G produce.

1. **H** — result envelope (`resultType`, `serverInfo`, `extensions`) and the
   outright removals. Unblocks everything; also flushes out every response path.
2. **F-fix** — `-32004` → `-32022`, reserve `-32021`, rewrite the stale 403
   rationale, add the (corrected) CI guard. Tiny, and stops shipping an off-spec
   error code.
3. **C** — header validation + required cache fields. Self-contained, and the
   cache fields are what downstream consumers are waiting on.
4. **G** — `subscriptions/listen`. Retires the GET stream for good.
5. **B** — MRTR. Largest, and the only one with a real security surface
   (`requestState`).
6. **I** + **VCB** — Tasks extension and the View/Compose/Bridge helpers.
7. **Flip the default** to `transport: "stateless"`, keeping stateful behind the
   flag for at least one minor.

## Server Migration — `@casys/mcp-server`

The plan is organised into five tracks. Tracks A, C, D, E are independent and
can run in parallel. Track B depends on A.

### Track A — Stateless Transport (effort: L)

Replace the stateful HTTP transport with a stateless one. During the migration
window the new stateless transport is opt-in behind a
`transport: "stateful" | "stateless"` option (default `"stateful"`), so the
legacy stateful path stays the default and consumers migrate incrementally. The
default flips to `"stateless"` once `2026-07-28` ships (see Non-Goals: the
stateful path then lives on behind the same option for at least one more minor
release).

**Affected code**:

| Location                                                                                | Action                                                                                                                                             |
| --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mcp-app.ts` — `initialize` session-creation block                                      | Drop `initialize`-driven session creation and the `sessions.has(reqSessionId)` validation block.                                                   |
| `mcp-app.ts` — GET/SSE route header read                                                | Remove the `mcp-session-id` header read on GET/SSE routes.                                                                                         |
| `mcp-app.ts` — advertised `protocolVersion`                                             | Update advertised `protocolVersion` to `2026-07-28` (negotiated, not hard-coded).                                                                  |
| `packages/server/src/types.ts:445,577` and `packages/server/src/middleware/types.ts:25` | Remove `sessionId?: string` from `ToolContext`, `AppToolCall`, `HttpRateLimitContext`, `Middleware`.                                               |
| `packages/server/src/runtime/`                                                          | Introduce a stateless POST handler that reads `_meta.protocolVersion` from the request body and dispatches to the existing tool/resource handlers. |

**Actual status (✅ published 0.21.0 — SEP-2575-conformant)**:

- ✅ opt-in `transport: "stateful" | "stateless"` flag; session ignored in
  stateless mode; `initialize` replies without `Mcp-Session-Id`; GET `/mcp`
  → 405.
- ✅ Per-request version read from
  `params._meta["io.modelcontextprotocol/protocolVersion"]` (the earlier
  top-level reading was settled in favour of the namespaced `_meta` key per
  SEP-2575).
- ✅ SEP-2575 conformance: error codes `-32602` (missing field) / `-32004`
  (unsupported version, with `data.{supported,requested}`);
  `MCP-Protocol-Version` header validated **tolerantly** (must match `_meta`
  when present, optional otherwise for backward-compat); `server/discover` RPC
  implemented; per-request `clientInfo`/`clientCapabilities` exposed to handlers
  (A2). `ping`/`initialize` intentionally retained in stateless for
  backward-compat.
- ✅ Acceptance: round-robin across two instances proven (A3) with a conformant
  in-house client (the stock SDK 1.29 client does not yet speak the stateless
  wire format).
- ↩ Deferred (non-blocking): dropping `sessionId?` from the context types and
  extracting the handler into `runtime/` were judged unnecessary for conformance
  and skipped to preserve backward-compat.

**Acceptance criteria**:

- A single `POST /mcp` request, with no prior handshake, succeeds when carrying
  a valid `_meta.protocolVersion`.
- No `Mcp-Session-Id` header is emitted or required.
- Round-robin across two instances behind a load balancer (no shared state)
  returns consistent results.

### Track B — Multi Round-Trip Requests (effort: L)

Replace server-initiated requests (`sampling/createMessage`,
`elicitation/create`, `roots/list`) with the `InputRequiredResult` pattern. The
client retries the original request — under a **new** JSON-RPC id — echoing back
`inputResponses` and the opaque `requestState`.

Decommissioning the GET/SSE push channel moved to **Track G**: change
notifications relocate to `subscriptions/listen` rather than disappearing.

**Wire shape** (final spec, not the RC sketch):

- `inputRequests` and `inputResponses` are **maps** keyed by server-assigned
  identifiers, unique within the request. Values are `ElicitRequest` /
  `CreateMessageRequest` / `ListRootsRequest` and their matching results.
- `requestState` — **the real name of what this plan called a "continuation
  token"**. Opaque to the client, which **MUST** echo it back verbatim.
- Every `InputRequiredResult` **MUST** carry at least one of `inputRequests` or
  `requestState`, and is only valid on `tools/call`, `resources/read`,
  `prompts/get`.
- A server **MUST NOT** emit an input request for a capability the client did
  not declare — check `io.modelcontextprotocol/clientCapabilities` from `_meta`
  (already exposed per-request since 0.21.0, track A2).
- If the client returns incomplete `inputResponses`, reply with a **new**
  `InputRequiredResult`, not an error.

**Affected code**:

| Location                                                                                                                                         | Action                                                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `mcp-app.ts` — the `sseClients` map                                                                                                              | Moved to Track G — see `subscriptions/listen`.                                                                                                                                                                           |
| `mcp-app.ts` — the GET `/mcp` SSE route                                                                                                          | Moved to Track G — the GET route becomes 405; the stream moves to the `subscriptions/listen` POST response.                                                                                                              |
| `packages/server/src/mcp-app.ts:1901` (`sendToSession`), `1947` (`broadcastNotification` — the plan's `broadcastToAll` is the wrong symbol name) | Re-architect around responses carrying `InputRequiredResult`; no more out-of-band push. Note: the line numbers in this section are indicative — they have drifted ~+25 lines on `spec/2026-07-28-track-a`.               |
| `packages/server/src/types.ts`                                                                                                                   | Introduce `InputRequests`, `InputResponses`, `InputRequiredResult`; integrate in the tool / resource / prompt result unions.                                                                                             |
| `packages/server/src/mrtr/request-state.ts`                                                                                                      | Seal and verify `requestState`. **Treat it as attacker-controlled input.** HMAC-SHA256 binds the authenticated principal, a short TTL, and a digest of the originating method + salient params.                          |
| `packages/server/src/mrtr/replay-store.ts`                                                                                                       | Atomically consume the signed nonce before handler dispatch. The default memory store protects one continuously running process; multi-instance or restart-safe deployments inject one durable shared `MrtrReplayStore`. |

**Acceptance criteria**:

- A tool can return `InputRequiredResult` instead of a final result.
- The retry lands on a _different_ instance and completes — proving no
  server-side state beyond `requestState`.
- `requestState` replayed by a different principal, after its TTL, or against a
  different method is rejected.
- Tampered `requestState` fails verification and never reaches business logic.
- A second use of the same signed nonce is rejected before business logic. One
  shared atomic store is required to preserve that invariant across instances
  and restarts.

### Track C — Routing Headers & Cache Fields (effort: M)

⚠️ **Corrected 2026-07-30.** The RC-era version of this track said "emit
`Mcp-Method` and `Mcp-Name` headers **on responses**". That is wrong in both
direction and obligation: they are **request** headers the _client_ must send,
and the server's job is to **validate** them against the body. Getting this
backwards would have shipped a no-op. Nor is the track "non-breaking": a
conformant server rejects requests that omit the headers.

**Affected code**:

| Location                                                                             | Action                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/server/src/mcp-app.ts` (stateless POST entry)                              | Validate `Mcp-Method` against `method` and `Mcp-Name` against `params.name` / `params.uri` (`tools/call`, `resources/read`, `prompts/get`). Mismatch or missing → HTTP 400 + JSON-RPC `-32020`.           |
| idem                                                                                 | Decode the `=?base64?{b64}?=` sentinel on `Mcp-Name` / `Mcp-Param-*` **before** comparing to the body. Compare integers numerically, not as strings. Header _names_ compare case-insensitively.           |
| idem                                                                                 | Harden `MCP-Protocol-Version`: currently validated tolerantly (0.21.0). It is now REQUIRED and a mismatch with `_meta` → `-32020`. Absent header → reject, unless we opt into the pre-`2025-06-18` grace. |
| Tool registration + `tools/list`                                                     | Support the `x-mcp-header` annotation on primitive, statically-reachable `inputSchema` properties; validate any recognized `Mcp-Param-{Name}` against the argument at that exact property path.           |
| `tools/list`, `prompts/list`, `resources/list`, `resources/read`, `…/templates/list` | Emit **required** `ttlMs` (ms) and `cacheScope` (`"public"` \| `"private"`) per `CacheableResult`, sourced from per-tool / per-resource registration metadata.                                            |
| `tools/list`                                                                         | Return tools in a deterministic order (SHOULD — helps client caches and LLM prompt cache hit rates).                                                                                                      |

**Acceptance criteria**:

- A POST missing `Mcp-Method` is rejected with 400 + `-32020`.
- A POST whose `Mcp-Name` disagrees with `params.name` is rejected with
  `-32020`, including when the header arrives base64-encoded.
- A tool registered with a TTL surfaces `ttlMs` and `cacheScope` on
  `tools/list`.
- Two consecutive `tools/list` calls return the same order.

### Track F — Error Codes (effort: S)

Change the missing-resource error code from `-32002` to `-32602`. Audit all
`JSON-RPC` error responses in `packages/server/src/` for similar non-standard
codes.

**Status: ✅ published 0.21.0.** The missing-resource `-32002 → -32602` change
had already landed in 0.20.0. In 0.21.0 the 401/403 ambiguity was resolved:

- `createForbiddenResponse` (`auth/middleware.ts`) now returns a 403-specific
  code **`-32002`** (distinct from the 401's `-32001`). ⚠️ Decision changed from
  this plan's original suggestion of `-32003`: SEP-2575 **reserves `-32003`**
  for `MISSING_REQUIRED_CLIENT_CAPABILITY`, so reusing it for "forbidden" would
  collide in stateless mode. `-32002` is free in both the SDK `ErrorCode` enum
  and SEP-2575.
- The 403 now emits
  `WWW-Authenticate: Bearer resource_metadata="...",
  error="insufficient_scope", error_description="<scopes>"`
  (RFC 6750/9728). `createForbiddenResponse` takes the resource metadata URL;
  the `AuthError` call site passes `error.resourceMetadataUrl`. A Codex review
  caught that the HTTP pre-authenticated path (`createAuthMiddleware`
  early-return on a pre-verified `authInfo`) left `resourceMetadataUrl` empty —
  fixed by populating `ctx.resourceMetadataUrl` before that early-return.
- ~~`-32602` "Unknown tool" → `-32601`~~ **Rejected by fact-check**:
  `tools/call` is the JSON-RPC method and the tool name is a _parameter_, so
  `-32602` (InvalidParams) is correct. **No change.** **Reopened 2026-07-30 —
  the final spec renumbered these codes.** The spec now partitions the JSON-RPC
  server-error range: `-32000`..`-32019` stays implementation-defined (existing
  SDK usage grandfathered), `-32020`..`-32099` is reserved for the
  specification. Consequences:

| Code                              | RC (what we shipped) | Final        | Action                                                                 |
| --------------------------------- | -------------------- | ------------ | ---------------------------------------------------------------------- |
| `UnsupportedProtocolVersion`      | `-32004`             | **`-32022`** | ✅ `mcp-app.ts:230`                                                    |
| `HeaderMismatch`                  | `-32001`             | **`-32020`** | ✅ `mcp-app.ts:221` — header/body version mismatch                     |
| `MissingRequiredClientCapability` | `-32003`             | **`-32021`** | ✅ reserved `mcp-app.ts:227`, no emitter yet                           |
| 403 forbidden                     | `-32002`             | **`-31403`** | moved out of the reserved range — the spec MUST NOTs emitting `-32002` |
| resource not found                | `-32602`             | `-32602`     | unchanged                                                              |

The 403 choice of `-32002` was justified above by SEP-2575 reserving `-32003`.
That reservation moved to `-32021`, so the original argument no longer holds —
`-32002` remains correct for a different reason: it sits in the grandfathered
implementation-defined range, where a server-specific meaning is legitimate.
Rewrite the inline comment; leave the code alone.

**Resolved 2026-07-30 — the grep-guard is dropped, deliberately.** The earlier
TODO was also inverted: it would have guarded against `-32020`/`-32022`, which
are now the _mandated_ codes. Rather than invert the pattern, the guard is
replaced by two stronger mechanisms:

1. **Named constants** (`MCP_HEADER_MISMATCH`,
   `MCP_UNSUPPORTED_PROTOCOL_VERSION`,
   `_MCP_MISSING_REQUIRED_CLIENT_CAPABILITY`) — a numeric literal no longer
   appears at the emission site, so there is nothing for a grep to catch.
2. **Wire-level assertions** in `http-server_test.ts` and
   `stateless-interop_test.ts` — they assert the code a client actually
   receives. A grep proves a string is absent from the source; a test proves the
   protocol is right. Only the latter catches a constant that is correct but
   wired to the wrong condition.

If a guard is ever wanted again, the regressions worth catching are
`-32001`-as-HeaderMismatch and `-32004`-as-UnsupportedVersion — the RC values.

### Track G — `subscriptions/listen` (effort: M–L)

New in the final spec; absent from the RC-era plan. One RPC replaces both the
HTTP GET stream and `resources/subscribe` / `resources/unsubscribe` (the latter
were never implemented here, so there is nothing to remove).

**Shape**:

- `subscriptions/listen` params carry a `notifications` filter:
  `toolsListChanged`, `promptsListChanged`, `resourcesListChanged` (booleans)
  and `resourceSubscriptions` (array of URIs). All optional. The server **MUST
  NOT** send types the client did not request.
- The response is itself a long-lived SSE stream. The **first** message **MUST**
  be `notifications/subscriptions/acknowledged`, echoing the subset the server
  agreed to honour (unsupported types omitted).
- Every message on the stream carries `io.modelcontextprotocol/subscriptionId`
  in `_meta` — the JSON-RPC id of the `subscriptions/listen` request. Multiple
  concurrent subscriptions are allowed and demultiplexed by this id.
- Request-scoped notifications (`notifications/progress`,
  `notifications/message`) **must not** travel on this stream — they stay on the
  response stream of the request they relate to.
- Graceful closure: reply to the original request with an empty
  `resultType: "complete"` result before closing.
- Emit `X-Accel-Buffering: no`, and periodic SSE comment lines (`:\r\n`) as
  keep-alive.
- Cancellation on HTTP = the client closing the stream. The server **MUST**
  treat a closed response stream as cancellation of that request and send
  nothing further for it. `notifications/cancelled` is stdio-only now.
- No resumability: `Last-Event-ID` and SSE event ids are gone. A broken stream
  loses the in-flight request; the client re-issues it with a new id.

**Affected code**: the `sseClients` map and the GET `/mcp` route in
`packages/server/src/mcp-app.ts` (~`:232`, ~~`:1297–1382`), plus `sendToSession`
/ `broadcastNotification` (~~ `:1901`, `:1947`) which become subscription-scoped
fan-out keyed by subscription id instead of session id. Line numbers are
indicative — they have drifted since this plan was written.

### Track H — Per-Result Envelope & Removals (effort: M)

Mechanical but touches every response path. Cheap per site, wide blast radius —
worth landing before B, C and G so those tracks build on a conformant envelope.

| Item                                                                                                                                           | Status                                                                                           |
| ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `resultType: "complete"` on **every** result                                                                                                   | ✅ `stampResult()`                                                                               |
| `io.modelcontextprotocol/serverInfo` in each result's `_meta` (SHOULD)                                                                         | ✅ merged, never replacing a tool's own `_meta`                                                  |

Note on backward compatibility: a client speaking `2025-11-25` or earlier omits
`resultType`, and per the spec such results are read as `"complete"`. Our
stateful path can therefore keep emitting envelopes without `resultType` while
the stateless path adds it.

**Audit finding — SSE resumability is still in the code.** `Last-Event-ID` is
read at `mcp-app.ts:1457` and the per-client `lastEventId` is tracked at `:102`,
`:1495`, `:1500`, `:2281`. This is **not** a conformance bug: the whole path
hangs off `GET /mcp`, which already returns 405 in stateless mode, so it is
reachable only from the stateful transport where `2025-11-25` legitimately
supports resumability. It dies with the GET route in Track G — listed here so
the next reader does not re-discover it and assume Track H missed something.

### Track I — Tasks Extension (effort: M)

**Unblocked**: the RC-era non-goal ("out of scope until the extension API is
final") no longer applies — Tasks shipped as the official
`io.modelcontextprotocol/tasks` extension (SEP-2663).

- Poll-based `tasks/get` replaces the blocking `tasks/result`.
- New `tasks/update` for client→server input on a running task.
- `tasks/list` is gone.
- Servers **may** return task handles unsolicited — no per-request opt-in.
- Declare it under `ServerCapabilities.extensions` (needs Track H).

Downstream driver: `@casys/mcp-erpnext` has several tools well over the
synchronous comfort zone (kanban board loads, revenue aggregations, stock
treemap scans) waiting on this API.

## View Migration — `@casys/mcp-view`

`@casys/mcp-view` is a thin wrapper over `@modelcontextprotocol/ext-apps`' `App`
class. The official MCP Apps extension (SEP-1865) ships with `2026-07-28` and
validates the package's positioning. No structural migration is required, but
two gaps are worth closing as the spec stabilises:

1. **Missing helpers on `AppContext`** — the spec defines iframe→host requests
   such as `ui/request-display-mode`, `ui/update-model-context`, and
   `ui/open-link`. Today these are reachable only via the `ctx.app` escape
   hatch. Expose typed helpers: `ctx.requestDisplayMode`,
   `ctx.updateModelContext`, `ctx.openLink`.
2. **UI resource metadata** — the spec defines `_meta.ui.csp`,
   `_meta.ui.permissions`, and `_meta.ui.domain` on UI resources. These are
   server-side concerns (`@casys/mcp-server` resource registration) but should
   be modelled so that View consumers do not bypass them. Add a small
   `defineUiResource()` helper in `@casys/mcp-server` (or `@casys/mcp-compose`)
   that produces a spec-correct resource shape.

The internal router (`packages/view/src/router.ts`) remains a differentiator:
the MCP Apps spec does not define an intra-iframe navigation primitive, so
wrapping it inside View continues to add value.

## Compose & Bridge

No protocol-level changes are required. Compose and Bridge re-use the server's
transport. Once Track A lands, they pick up the stateless transport for free.

## Validation Strategy

1. **Per-track POC** on a `spec/2026-07-28` branch. Each track lands as its own
   PR with tests.
2. **Independent review** of each PR via Codex (sub-agent reviewer) on
   architecture, safety, and conformance axes.
3. **Behind a feature flag** until the official `2026-07-28` spec ships, so
   `main` continues to publish a stable `2025-11-25`-compatible release.
4. **Interop matrix**: validate against at least one reference MCP host (Claude
   Code, MCP Inspector) on both the stateless transport and the legacy stateful
   path.

## Non-Goals

- Removing the Sampling / Logging **features**. The 12-month deprecation clock
  started 2026-07-28; removal lands after 2027-07-28. Note the distinction: the
  _features_ are deprecated, but the `logging/setLevel` and `ping` _methods_
  were **removed outright** — those go in Track H, not here.
- ~~Implementing the Tasks extension.~~ **Lifted 2026-07-30** — the extension is
  final. See Track I.
- Migrating downstream consumers automatically. The stateful transport remains
  available behind a flag for at least one minor release after the default flips
  to `"stateless"`.
